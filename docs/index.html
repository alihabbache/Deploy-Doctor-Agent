Deploy Doctor Agent

A rule-based agent (no LLM yet). Feed it a failed CI/CD run. It tells you what kind of failure it is, shows the evidence, and proposes the top 3 fixes as diffs.

github.com/alihabbache/Deploy-Doctor-Agent · proof of concept v0.1.0 · Python standard library only

ProblemFailed deployments waste hours. The log is long, but the cause is usually a known pattern.
SolutionAn agent that ingests the failed run, classifies it, and proposes 3 ranked fixes with diffs.

Fix #1: Confirm `ghcr.io/acme/checkout-api:3f9a1c2` was actually pushed  [risk: low]
Deploy jobs often run before, or without, the push that creates the tag. The registry reported the reference as not found.
$ docker manifest inspect ghcr.io/acme/checkout-api:3f9a1c2

Fix #2: Make the release roll back automatically on failure  [risk: low]
`--atomic` reverts a failed Helm upgrade, so a bad release never stays half-deployed.
--- a/.github/workflows/deploy.yml
+++ b/.github/workflows/deploy.yml
@@ -1 +1 @@
-      - run: helm upgrade app ./chart --install
+      - run: helm upgrade app ./chart --install --atomic --timeout 5m

Fix #3: Add an imagePullSecret for `ghcr.io/acme/checkout-api:3f9a1c2`  [risk: medium]
ImagePullBackOff means the node cannot fetch the image: wrong tag, missing push, or no pull credentials. The registry said the tag was not found, so check the push first.
--- a/k8s/deployment.yaml
+++ b/k8s/deployment.yaml
@@ -1,4 +1,6 @@
     spec:
+      imagePullSecrets:
+        - name: regcred

How it works

1. IngestStrip ANSI codes, timestamps and CI prefixes. Keep original line numbers. Detect GitHub, GitLab, Jenkins or CircleCI.
2. Classifyweighted rules score 8 categories. Output: ranked categories, tags, evidence lines and confidence.
3. ExtractPull concrete names: env var, package, image, test, lock ID, IAM action, TS error.
4. ProposeFill the 40 templates with those names. Rank by fit × category share. Keep 3.
5. ReportText, JSON or Markdown (for PR comments).

Categories: auth dependency build test config infra rollout. A log that matches nothing returns unknown with no fixes. It refuses to guess.

Machine-readable output (--json), trimmed:

{
  "category": "config",
  "confidence": 0.75,
  "entities": {
    "env_var": "DATABASE_URL",
    "exit_code": "1"
  }
}

Design decisions

  • Rules first, LLM later. A POC should be deterministic, offline and free, so every result can be explained and tested. An LLM fits best as a fallback for logs the rules can't classify.
  • Confidence is capped at 95%. It measures how strongly rules matched and how far ahead the winner is. It is not a probability.
  • Every fix is a proposal. Each carries a risk level. High-risk fixes (for example terraform force-unlock) are labelled. Nothing is applied automatically.
  • Evidence is cited by line number so a human can verify the diagnosis in seconds.

What I'd measure to prove the impact

The impact claim (lower MTTR) is a hypothesis, not a result. The POC has not been tried on real incidents. To test it:

  • Time to first correct hypothesis: failed run → engineer knows the cause. Compare with and without the agent.
  • Top-3 hit rate: share of failures where the right fix is in the 3 proposed. Target ≥ 70% before wider rollout.
  • Unknown rate: share of logs the rules cannot classify. It drives which rules to write next.
  • Wrong-but-confident rate: high-confidence misdiagnoses. This is the trust-killing metric, so keep it near zero.

Known limits

  • Diffs are templates. They show the shape of the change with placeholders such as <ACCOUNT_ID>, not a patch against your real files.
  • Only the log is analysed. It doesn't see the repo, the previous green run, or the commit diff.
  • English log messages only. Only one root cause is reported. When several categories match, the others are listed as "also matched".
  • Rules are regexes, so a new tool with a new error format needs a new rule.
